## 2. INV-15 — CONSERVACIÓN DE VALOR (formalización solicitada por el dueño)

### 2.1 Definición en unidades y eventos (sin ambigüedad contable)

Ámbito: por `(store_id, product_id, ventana [t0,t1])`, unidades base, CUP normalizado.

```text
V(t) = stock(t) × ca(t)                 [ca = cost_average vigente — bajo D-01=A]

ΔV ≡ V(t1) − V(t0)

IDENTIDAD POR TIPO DE EVENTO (cada evento declara su aporte con signo):

  RECEPCIÓN / TRANSFER-IN / AJUSTE+ / PRODUCCIÓN-IN (blend):
      aporte = + qty_in × uc_event
      (exacto: (S+q)·ca_nuevo − S·ca_prev = q·uc  ⇔  definición de blend)
      → SIN varianza.

  VENTA / TRANSFER-OUT / AJUSTE− / PRODUCCIÓN-OUT (salida pura, WAC constante):
      aporte = − qty_out × WAC_prev
      (ca no cambia ⇒ ΔV = −q·ca = −q·uc_event)
      → SIN varianza.

  DEVOLUCIÓN (A1 reversión neutra, c_rev = cost_at_sale original):
      aporte = + qty_dev × WAC_vigente        [efecto real en stock×ca]
      varianza_base = + qty_dev × (WAC_vigente − c_rev)   [línea etiquetada; 0 si c_rev = WAC]
      aporte_contable = aporte − varianza_base = + qty_dev × c_rev   [lo que acredita el kardex]

  REVERSAS compensatorias: aporte = ± qty × uc congelado + varianza equivalente si la base difiere.

IDENTIDAD GLOBAL (INV-15):

  V(t1) − V(t0) = Σ aportes_contables(eventos) + Σ varianzas_base(eventos)  ±  tolerancia

  con tolerancia = GREATEST(0.01, 1e-6 × max(|V(t0)|, |V(t1)|)) por producto/tienda/ventana.
```

### 2.2 Probe SQL (borrador para el harness; mismo estándar que 65)

```sql
-- INV-15 VALUE-CONSERVATION · violaciones por (store, product, ventana)
-- Requiere: columnas/varianza materializada según resolución de CR-W6-3 (línea etiquetada
-- o ventana marcada). Hasta entonces, versión 'pre' solo informativa.
WITH ev AS (
  SELECT sm.store_id, sm.product_id, sm.movement_date,
         sm.quantity_change,
         CASE
           WHEN sm.movement_type IN ('purchase','transfer_in','initial')
             THEN  sm.quantity_change * sm.unit_cost              -- entrada: +q×uc (blend exacto)
           WHEN sm.movement_type IN ('sale','transfer_out','production_out')
             THEN  sm.quantity_change * sm.unit_cost              -- salida pura: −q×WAC (=uc congelado)
           WHEN sm.movement_type = 'adjustment' AND sm.quantity_change > 0
             THEN  sm.quantity_change * sm.unit_cost              -- ajuste+ blend
           WHEN sm.movement_type IN ('return')                    -- devolución A1
             THEN  sm.quantity_change * sm.unit_cost              -- +q×c_rev (aporte contable)
           ELSE NULL                                              -- tipos no valorados: 'void' etc.
         END AS aporte_contable
  FROM stock_movements sm
  WHERE sm.movement_date >= :t0 AND sm.movement_date < :t1
),
deltas AS (
  SELECT store_id, product_id, SUM(aporte_contable) AS total_aportes
  FROM ev GROUP BY 1,2
),
v AS (
  SELECT p.store_id, p.id AS product_id,
         p.stock_current * p.cost_average AS v_end
  FROM products p WHERE NOT p.is_service
),
v0 AS (  -- valor inicial por producto en t0 (requiere snapshot/history — misma dependencia que INV-04/05)
  SELECT ... -- [SCHEMA-DEPENDENCY: inventory_history o snapshot por ventana]
)
SELECT v.store_id, v.product_id
FROM v
JOIN deltas d ON d.store_id=v.store_id AND d.product_id=v.product_id
-- JOIN v0 ...
WHERE ABS((v.v_end - v0.v_start) - (d.total_aportes + COALESCE(var.sum_varianza,0)))
      > GREATEST(0.01, 1e-6 * GREATEST(ABS(v.v_end), ABS(v0.v_start)));
```
