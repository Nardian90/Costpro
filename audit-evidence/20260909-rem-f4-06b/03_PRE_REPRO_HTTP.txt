## ANÁLISIS DEL RESULTADO (hallazgo adicional — OPEN FINDING OF-1)

El HTTP 500 previsto por la directiva se demostró. Sin embargo, el error que
llega a la respuesta HTTP NO es el del trigger de auditoría: la ruta
(src/app/api/fiscal-close/route.ts, líneas 75-80) invoca SIEMPRE
  supabase.rpc('lock_fiscal_period', { p_store_id, p_user_id, p_year, p_month })
pero la firma REAL del RPC es
  lock_fiscal_period(p_store_id uuid, p_year integer, p_month integer)
— NO acepta p_user_id → PostgREST no resuelve la función → 500.

Esto significa que el camino HTTP del lock está roto a NIVEL DE RUTA de forma
independiente del trigger de auditoría: incluso con el trigger corregido, el
lock HTTP seguiría en 500 hasta corregir ese desajuste (en ruta o firma RPC).

CLASIFICACIÓN (directiva §0/§25):
  OF-1 (OPEN FINDING) — defecto de wiring ruta→RPC, en src/, clase hermana,
  FUERA del alcance quirúrgico de REM-F4-06b (cuya solución esperada es
  DB/migración; "NO modifiques src/ salvo que sea estrictamente necesario
  para esta remediación"). NO se corrige en este gate. Recomendación: gate de
  seguimiento (REM-F4-06c) para alinear la llamada de ruta con la firma RPC
  o ampliar la firma, más pruebas HTTP lock de extremo a extremo.
